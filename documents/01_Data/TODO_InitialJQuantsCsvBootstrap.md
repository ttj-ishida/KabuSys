# TODO: 初回 J-Quants CSV 一括取り込み要件メモ

- ステータス: 未着手
- 目的: 初回環境構築時に、J-Quants の大量ヒストリカルデータを CSV ダウンロード経由で取り込み、分析・バックテスト・実運用の初期データ基盤を構築するための要件を整理する
- 対象: 初回データ投入（bootstrap）、通常運用前の大量データ取り込み

---

## 1. 背景

通常運用では、J-Quants API を用いた差分更新を前提とする。

しかし初回環境構築時は、以下の理由により API 差分取得だけでは非効率、または不十分となる可能性が高い。

- 過去の株価・財務データを大量に取得する必要がある
- API 呼び出し回数制限がある
- 初回ロードだけで数年分の履歴が必要になる
- バックテスト再現性のため、なるべく一括で安定した初期データを揃えたい

このため、初回ロードは **通常運用の差分更新ジョブとは別に、CSV ダウンロードを利用した bootstrap 処理** として設計する必要がある。

---

## 2. この処理の位置づけ

この処理は、通常の `data_update_job` とは別物とする。

### 2.1 bootstrap の役割

- 初回環境構築時に大量の履歴データを投入する
- 通常運用開始前の土台を作る
- バックテストに必要な十分な履歴長を確保する

### 2.2 通常運用との差分

- bootstrap
  - 大量一括投入
  - CSV ベース
  - 初回中心、必要時再実行
- 通常運用
  - 日次差分更新
  - API ベース
  - 毎営業日実行

---

## 3. 対象データ

初回 bootstrap で取り込む候補を整理する。

### 優先度高

- 株価（日足 OHLCV）
- 銘柄マスタ
- 財務データ
- JPX カレンダー

### 優先度中

- コーポレートアクション関連データ
- 上場 / 廃止履歴に関わる補助情報

### 優先度低

- ニュースデータ
  - J-Quants 由来ではなく別系統のため、bootstrap とは分離してもよい

---

## 4. 取り込み方式の基本方針

### 4.1 CSV ダウンロードを前提とする

初回ロードでは、J-Quants の一括ダウンロード CSV を利用する前提で設計する。

### 4.2 Raw / Processed を分離する

既存の Data Platform 設計に合わせ、CSV も一度 Raw として保持し、その後 Processed に整形する。

流れ:

```text
J-Quants CSV ダウンロード
  -> Raw 保存
  -> スキーマ検証
  -> クリーニング / 正規化
  -> Processed テーブル投入
```

### 4.3 冪等性を確保する

同じ CSV を再投入しても、重複や破損が発生しない設計にする。

---

## 5. 初回ロードで満たすべき要件

### 5.1 大量データ対応

- 数年分の株価履歴を一括投入できる
- メモリ超過を避ける
- 可能ならストリーミングまたは分割読込を使う

### 5.2 再実行可能性

- 途中失敗しても再開できる
- 同一ファイル再投入で重複しない
- 部分再実行が可能

### 5.3 データ品質管理

- ヘッダ検証
- 型検証
- 必須列検証
- 重複検知
- 異常日付検知
- 銘柄コード正規化

### 5.4 監査性

- どの CSV をいつ投入したかを追跡可能にする
- 元ファイル名、取得日、件数、ハッシュ値を保持する

### 5.5 通常運用との接続

- bootstrap 後に通常の API 差分更新へ自然に移行できる
- どこまで CSV で埋まっているかを判定できる

---

## 6. 想定フロー

### Step 1. CSV 取得

- J-Quants から一括ダウンロード
- ファイル命名規則を統一
- 取得日を記録

### Step 2. Raw 保存

- 生 CSV をそのまま保存
- 圧縮の有無も保持
- 元ファイル名、サイズ、ハッシュ値を記録

### Step 3. ロード前検証

- ファイル形式確認
- 必須列確認
- 文字コード確認
- 日付形式確認

### Step 4. Raw 取り込み

- Raw テーブルまたは Raw Parquet に投入
- 取り込み件数を記録

### Step 5. Processed 変換

- 重複除去
- 欠損処理
- 型変換
- 銘柄コード統一
- 調整価格処理との整合確認

### Step 6. 完了記録

- bootstrap 実行結果を記録
- どのデータ種別がどこまで投入完了したかを記録

---

## 7. 保存先の検討

### 7.1 Raw ファイル保存先

候補:

```text
data/bootstrap/raw/jquants/
```

構成例:

```text
data/bootstrap/raw/jquants/prices/2026-04-21/*.csv
data/bootstrap/raw/jquants/listed_info/2026-04-21/*.csv
data/bootstrap/raw/jquants/financials/2026-04-21/*.csv
```

### 7.2 変換後保存先

候補:

- Raw テーブル
- Raw Parquet
- Processed DuckDB テーブル

---

## 8. 必要なメタデータ

少なくとも以下を保持したい。

- データ種別
- 元ファイル名
- 保存パス
- 取得日
- 取込日時
- ハッシュ値
- レコード件数
- ステータス
  - `downloaded`
  - `validated`
  - `loaded_raw`
  - `loaded_processed`
  - `failed`
- エラー内容

必要なら専用テーブルを作る。

候補:

```text
bootstrap_load_history
```

---

## 9. 通常運用との境界

bootstrap 後は、通常運用に引き継げる必要がある。

そのために以下を明確にする必要がある。

- bootstrap の最終投入日
- 通常 API 差分更新の開始日
- 重複期間の扱い
- 初回差分更新時の冪等性確認

---

## 10. エラー時の扱い

想定エラー:

- CSV 破損
- 列不足
- 型不整合
- 日付不整合
- 重複大量発生
- 途中停止
- ディスク容量不足

要件:

- Fail-Fast するか、warning 付き継続にするかを定義する
- データ種別ごとに失敗を分離する
- 失敗時にどこまでロールバックするかを明確にする

---

## 11. パフォーマンス要件

初回ロードは大量データ前提のため、以下を考慮する。

- 分割読込
- バルクロード
- DuckDB / Parquet の活用
- 日付または銘柄単位でのチャンク化
- 中間ファイル削除ポリシー

---

## 12. ユーザー操作として必要なこと

初回 bootstrap では、ユーザーが以下を行う可能性がある。

- J-Quants から CSV をダウンロードする
- 所定ディレクトリへ配置する
- bootstrap 実行コマンドを起動する
- 完了レポートを確認する
- 失敗時に再実行する

このため、ユーザー向け手順書も将来的に必要となる。

---

## 13. 完了後に必要な確認

bootstrap 完了後は、最低限以下を確認する必要がある。

- `prices_daily` に必要期間のデータが入っている
- `stocks` が投入されている
- `financials` 系が投入されている
- `market_calendar` が投入されている
- バックテストに必要な最小履歴長が確保されている
- 通常 API 差分更新ジョブへ移行可能である

---

## 14. まず決めるべき仕様

### 優先度高

1. bootstrap 対象データ
2. Raw 保存方式
3. Processed への投入方法
4. 再実行 / 冪等性のルール
5. bootstrap 完了判定方法

### 優先度中

1. 専用メタデータテーブルを作るか
2. CSV 配置ディレクトリ規約
3. エラー時の継続 / 停止ポリシー

### 優先度低

1. 自動ダウンロード連携
2. 進捗ダッシュボード
3. 差分検知の高度化
