# RiskManagement.md

## 1. 目的

本ドキュメントは、日本株自動売買システムにおける **リスク管理方針および制御ロジック** を定義する。

自動売買システムでは、戦略の収益性よりも **リスク管理の設計がシステムの安定性と長期運用を決定する**。

本ドキュメントの目的は以下である。

- 想定外の損失を防止する
- システム障害による誤発注を防ぐ
- 市場環境悪化時の資産保全を行う
- 自動売買を長期運用可能な状態に保つ

---

# 2. リスク管理の基本原則

本システムでは以下の原則を採用する。

1. **単一戦略に依存しない**
2. **ポジションサイズを制御する**
3. **損失は小さく、利益は伸ばす**
4. **市場環境に応じてリスク量を調整する**
5. **システム異常時は即座に取引停止する**

---

# 3. リスク分類

本システムでは以下のリスクを管理対象とする。

## 3.1 市場リスク

市場価格変動による損失

例

- 株価急落
- 市場クラッシュ
- セクター暴落

対策

- ポジションサイズ制御
- 損切りルール
- 市場レジーム判定

---

## 3.2 流動性リスク

流動性不足により売買が成立しないリスク

例

- 出来高不足
- スプレッド拡大
- 板薄銘柄

対策

- 最低売買代金フィルタ
- 板厚監視
- 成行注文制限

---

## 3.3 システムリスク

システム障害による誤動作

例

- APIエラー
- ネットワーク障害
- プログラム例外

対策

- フェイルセーフ設計
- 冪等注文ID
- キルスイッチ

---

## 3.4 モデルリスク

戦略モデルが市場環境に適合しなくなるリスク

例

- 市場レジーム変化
- 過剰最適化
- AI誤判定

対策

- バックテスト比較
- AIスコア影響制限
- レジーム制御

---

# 6. 市場レジームによるリスク調整

市場を以下に分類する

| レジーム | リスク          |
| -------- | --------------- |
| Bull     | 通常            |
| Neutral  | やや縮小        |
| Bear     | 新規停止 / 縮小 |

- 新規建停止
- 保有縮小

# 14. ストレステスト・シナリオテスト

極端な市場状況でのシステム動作を検証するシナリオテストを `tests/test_stress_scenarios.py` で実施する。

## 14.1 マーケットクラッシュシナリオ

> **閾値比較仕様**: ドローダウンチェックは **厳密な超過（`drawdown > max_drawdown`）** でブロック。閾値ちょうど（`==`）は通過する。

検証内容:
- ドローダウン 5% は発注ブロックしない（閾値 15%）
- ドローダウン閾値ちょうど（15%）は通過（`>` 判定のため）
- ドローダウン 20% で `RiskManager.check_metrics()` が失敗
- `KillSwitch.evaluate()` が drawdown_alert=True で `kill.flag` を書き込む
- 複数回クラッシュ評価でも `kill.flag` が冪等（上書きしない）
- クラッシュ後もポジションは保持される（強制清算しない）
- ポジション評価額が全体利用率上限（80%）を超える新規発注は拒否される

**breadth_stop による BUY 停止（Issue #173 で追加予定）:**
- 25日移動平均上銘柄比率が 35% 未満の場合、`market_breadth.breadth_stop = True` となり新規 BUY を全件停止する
- この停止は `regime_score` や KillSwitch とは独立して動作する（SELL は停止されない）
- 騰落レシオ < 80 の場合は `regime_score` に −0.2 の補正を加えて bear 判定を強化する

## 14.2 API 接続遮断シナリオ

検証内容:
- 閾値未満のエラーではサーキットブレーカーが開かない
- 閾値（デフォルト 10 件）のエラーでサーキットブレーカーが OPEN になり全発注をブロック
- レート制限（5件/秒）超えのバースト発注が拒否される
- ウィンドウ経過後 HALF_OPEN → プローブ 1 件許可 → 成功で CLOSED に回復
- サーキットブレーカーとドローダウン超過の同時発生で両ガードが独立して機能する

## 14.3 流動性枯渇シナリオ

検証内容:
- ブローカーが全発注を拒否（`fill_mode=reject`）→ `OrderState.Rejected` に遷移
- 同一 signal_id への再発注が `DuplicateOrderError` でブロックされる（二重発注防止）
- ブローカーが約定しない（`fill_mode=never`）→ `OrderState.OrderSent` で保留・`broker_order_id` が DB に保存（Reconciliation 対象）
- 部分約定（`fill_mode=partial`）→ 50% 約定・`sync_order` 後に `PartialFill` に遷移
- 現金枯渇時の買い注文は余力不足で拒否・売り注文はブロックされない
- 連続 API エラーがサーキットブレーカーを発動させる
- 流動性の低い銘柄へのオーバーアロケーションがポジション上限（10%）で拒否される

# 15. まとめ

リスク管理は自動売買システムの最重要要素である。

本システムでは

- ポジションサイズ管理
- 損切りルール
- 市場レジーム制御
- AIリスク制御
- 発注安全機構
- キルスイッチ

を組み合わせることで、安全かつ長期的に運用可能な自動売買基盤を構築する。
