# TODO: 運用成績サマリーレポート設計メモ

- ステータス: 設計完了（仕様書: `docs/superpowers/specs/2026-04-29-performance-report-design.md`）
- 目的: 実運用における運用成績サマリーレポートの仕様を整理する
- 対象: 本番口座 / `paper_trading` 共通の成績レポート
- 出力形式: Markdown
- 集計単位: 日次 / 週次 / 月次

---

## 1. 背景

現行設計では、運用成績の元データとして以下が保持される。

- `portfolio_performance`
  - `date`
  - `equity`
  - `cash`
  - `drawdown`
  - `daily_return`
- `positions`
- `orders`
- `trades`

また、運用時には以下の確認が Runbook 上で求められている。

- 日次リターン
- ポジション一覧
- 取引履歴
- ドローダウン

しかし、これらは主にテーブル直接確認や監視ダッシュボード前提であり、**ユーザーが後から振り返れる形の成績サマリーレポート** は明確に定義されていない。

さらに、`paper_trading` ではゴーライブ判断用の検証レポートが存在する一方、本番運用と共通の成績レポート仕様にはなっていない。

---

## 2. このレポートの目的

このレポートは、以下を満たすことを目的とする。

1. 日々の運用結果を短時間で把握できる
2. 週次・月次で成績推移を振り返れる
3. 本番口座と `paper_trading` を同じ形式で比較できる
4. 損益だけでなく、リスクと取引状況も確認できる
5. 将来の改善・監査・レビューに使える

---

## 3. 基本方針

### 3.1 本番口座用と `paper_trading` 用を共通化する

レポートの章立て、指標、出力先、ファイル形式は共通化する。

差分はメタ情報として表現する。

例:

- `environment = live`
- `environment = paper_trading`

### 3.2 出力形式は Markdown に統一する

最初の設計対象は Markdown のみとする。

理由:

- 人間が読みやすい
- Git 管理しやすい
- Slack や Wiki に転記しやすい
- 本番 / paper の共通化がしやすい

### 3.3 集計単位は 3 種類

- 日次レポート
- 週次レポート
- 月次レポート

すべて同じ骨格を持たせつつ、粒度ごとに表示内容を変える。

---

## 4. レポート種別

## 4.1 日次レポート

目的:

- 当日の損益と状態を確認する
- 翌営業日に持ち越すべき注意点を把握する

主な読者:

- 運用者
- 管理者

## 4.2 週次レポート

目的:

- 1 週間の成績推移を確認する
- 勝ち負けの偏り、取引頻度、DD 悪化を振り返る

主な読者:

- 運用者
- レビュー担当

## 4.3 月次レポート

目的:

- 月単位の運用成績を評価する
- 本番 / paper の比較や、運用継続判断に使う

主な読者:

- 運用者
- 管理者
- 将来の監査 / 改善担当

---

## 5. 共通で必ず出す項目

以下は、日次 / 週次 / 月次すべてで共通とする。

### 5.1 メタ情報

- `environment`
  - `production` / `paper_trading`
- レポート種別
  - `daily` / `weekly` / `monthly`
- 集計期間
- レポート生成日時

### 5.2 資産サマリ

- 期首資産
- 期末資産
- 損益額
- 損益率
- 現金残高

### 5.3 リスクサマリ

- 期間末ドローダウン
- 期間中最大ドローダウン

### 5.4 取引サマリ

- 売買件数
- BUY 件数
- SELL 件数
- 約定件数
- 保有銘柄数（期末時点）

### 5.5 コメント / warning

- 成績上の注意点
- データ欠損や記録異常
- DD 超過などの重要イベント

---

## 6. 日次レポートで追加すべき項目

日次では、その日 1 日の運用状態を把握するために以下を追加する。

- 当日日次リターン
- 当日損益額
- 当日最大ドローダウン
- 当日終了時点の保有銘柄一覧
- 当日発生した注文 / 約定の要約
- 当日発生したリスクイベント

候補:

- 未約定注文残件
- Kill Switch 発動有無
- `rejected` 注文件数

---

## 7. 週次レポートで追加すべき項目

週次では、週間の推移と偏りを見るために以下を追加する。

- 日別損益一覧
- 日別リターン一覧
- 勝ち日数 / 負け日数
- 週間最大ドローダウン
- 週間の売買件数推移
- 週末時点の保有銘柄一覧

候補:

- 週間セクター偏り
- 週間のシグナル件数

---

## 8. 月次レポートで追加すべき項目

月次では、成績評価と比較用途を意識して以下を追加する。

- 日別または週別の損益推移要約
- 月間最大ドローダウン
- 月間売買件数
- 勝率
- 平均利益 / 平均損失
- 月末時点の保有銘柄一覧

候補:

- 本番 / paper 比較欄
- 月間主要イベント一覧
- 月間リスクイベント一覧

---

## 9. Markdown レポートの共通章立て案

すべてのレポートは、最低限以下の章立てを持つ。

1. Overview
2. Asset Summary
3. Risk Summary
4. Trade Summary
5. Positions
6. Warnings

### 日次での補強

- 当日注文 / 約定要約
- 当日イベント

### 週次での補強

- 日別一覧
- 週内推移

### 月次での補強

- 集計サマリ
- 比較・振り返り欄

## 10. ファイル命名と保存先

本番口座用と `paper_trading` 用で同一構造を使う。

保存先案:

```text
artifacts/performance/{environment}/daily/{yyyy-mm-dd}.md
artifacts/performance/{environment}/weekly/{yyyy}-W{ww}.md
artifacts/performance/{environment}/monthly/{yyyy-mm}.md
```

例:

```text
artifacts/performance/production/daily/2026-04-21.md
artifacts/performance/paper_trading/monthly/2026-04.md
```

## 11. 本番口座用と `paper_trading` 用の共通化方針

### 共通化するもの

- レポート形式
- 章立て
- 指標名
- warning ルールの基本形
- 保存先構造

### 環境差分として持つもの

- `environment`
- データソース DB
- 口座種別ラベル
- 本番専用 warning
- paper 専用 warning

### 設計上の注意

- 本番と paper で別コードパスを増やしすぎない
- レポート生成器は共通にし、入力データソースだけ切り替える

## 12. warning の初期案

### 日次

- 当日 DD が閾値超過
- `rejected` 注文が多い
- 約定が 0 件
- データ欠損

### 週次

- 連敗継続
- 週間 DD 悪化
- 取引件数が極端に少ない / 多い

### 月次

- 月間 DD 悪化
- 月次損益が大幅悪化
- 本番 / paper で乖離が大きい

## 13. 生成タイミング案

### 日次

- Market Close 後、`portfolio_performance` 記録完了後

### 週次

- 金曜引け後、または週末夜間バッチ後

### 月次

- 月末最終営業日引け後、または翌月初営業日前

## 14. 設計決定済み事項（Issue #195）

以下の設計が確定した。

- 週の定義: **JPX 営業日基準**（ISO 週番号ラベルを使用、`market_calendar.is_trading_day = true` で営業日数を算出）
- `paper_trading` / `live` の分離方法: **`portfolio_performance.env` 列**（`ALTER TABLE ADD COLUMN env VARCHAR DEFAULT 'live'`）
- CLI: `python -m kabusys.run_performance_report --type daily|weekly|monthly --env live|paper_trading`
- 比較: 別々のコマンド実行（同一レポート内の自動比較は後続フェーズ）
- warning 閾値: MVP では実装対象外（後続フェーズ）
- 集計ロジック: `portfolio_performance` のみ（positions/orders 詳細は後続フェーズ）
